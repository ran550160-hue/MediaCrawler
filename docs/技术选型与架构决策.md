# 技术选型与架构决策

## 1. 文档目的

本文记录 MediaCrawler Research MCP 的第一版技术选型结论，作为后续开发的架构决策依据。

输入来源：

- `docs/数据采集分析MCP_PRD.md`
- `docs/服务器登录态与飞书二维码方案.md`
- `docs/HERMES_AGENT选型建议.md`
- 当前已实现的 `analysis` 离线分析模块

结论原则：

- 优先满足 Hermes Agent 同机调用。
- 优先支持数据集沉淀、查询和复用。
- 避免第一版引入过重的分布式任务系统。
- MediaCrawler MCP 不绑定飞书 SDK，飞书交互由 Hermes 负责。

## 2. 总体结论

第一版采用以下技术组合：

```text
MCP 形态: stdio
任务元数据: SQLite + WAL
采集执行: subprocess
原始数据: JSONL
分析查询: DuckDB
报告输出: Markdown + HTML + JSON summary
登录态: Playwright persistent context 默认，CDP 可选，cookie import 兜底
二维码: qr_image_path 主通道，base64 可选
飞书集成: Hermes 负责，MediaCrawler MCP 不直接依赖飞书 SDK
```

核心抽象围绕：

- `Dataset`
- `Task`
- `Report`
- `Query`
- `LoginSession`

不围绕一次性的 `crawl_xhs`、`crawl_douyin`、`analyze_csv` 等零散命令建模。

## 3. MCP 服务形态

### 决策

第一版使用 stdio MCP。

### 理由

- MediaCrawler MCP 计划部署在 Hermes Agent 同一台服务器上。
- stdio 不需要开放端口、反向代理、TLS、鉴权和服务保活。
- Hermes 原生适合通过 stdio 管理本地 MCP server。
- 开发和调试成本最低。

### 暂缓

HTTP MCP 暂不作为第一版目标。

后续出现以下需求时再增加 HTTP 适配层：

- 多个 Agent 或多台机器共用同一个 MediaCrawler 服务。
- 需要 Web UI。
- 需要外部系统直接提交采集任务。
- 需要和 Hermes 生命周期解耦。
- 需要 webhook、远程队列或多用户网关。

### 设计要求

核心业务逻辑必须放在可复用 Python package 中。stdio MCP 只是适配层，后续可以再增加 HTTP MCP 适配层。

## 4. 任务执行与状态管理

### 决策

使用 SQLite 存储任务元数据，使用 subprocess 执行采集任务。

### SQLite 负责

- `datasets`
- `tasks`
- `login_sessions`
- `reports`
- `accounts`
- 简要运行日志索引

SQLite 开启 WAL 模式，满足单机多进程读写需求。

### subprocess 负责

每个采集任务通过独立 subprocess 调用 MediaCrawler 采集逻辑。

### 理由

- 采集任务可能持续数分钟到数十分钟，不适合阻塞 MCP tool call。
- Playwright 爬虫涉及浏览器进程、事件循环、页面崩溃和登录态，subprocess 隔离比线程更稳。
- subprocess 崩溃不应拖垮 MCP server。
- SQLite 足够支撑第一版单机任务状态，不需要 Celery、Redis 或 RQ。

### 暂缓

第一版不引入：

- Celery
- Redis Queue
- 分布式任务队列
- 独立任务调度服务

### 风险

如果 Hermes 或 MCP server 进程被杀，正在运行的 subprocess 可能中断。第一版接受该风险，但任务状态必须能标记为：

- `interrupted`
- `failed`
- `unknown`

后续如果需要强任务恢复，再考虑常驻 worker 或 HTTP 服务。

## 5. 数据集存储

### 决策

采用 JSONL + DuckDB + SQLite 的三层存储。

```text
~/.mediacrawler-mcp/
  metadata.sqlite
  datasets/
    ds_20260627_ai_coding_side_hustle/
      dataset.json
      raw/
        xhs_contents.jsonl
        xhs_comments.jsonl
        dy_contents.jsonl
        dy_comments.jsonl
      analysis.duckdb
      reports/
        report.md
        report.html
        summary.json
        charts/
```

### JSONL 负责

- 原始采集归档。
- 失败恢复。
- 审计和问题排查。
- 后续重新 normalize。

### DuckDB 负责

- 内容和评论表查询。
- 多关键词对比。
- 平台对比。
- Top 内容排序。
- 评论检索。
- 报告统计。

### SQLite 负责

- 数据集元信息。
- 任务状态。
- 登录会话。
- 报告索引。

### 暂缓

第一版不强制生成 Parquet。

理由：

- 当前项目没有 DuckDB 和 Parquet 相关依赖。
- 直接 JSONL normalize 到 DuckDB 更简单。
- Parquet 可在数据量明显增大后再引入。

## 7. MCP 工具接口

第一版工具数量保持少而深。

## 8. 登录态管理

### 决策

默认使用 Playwright persistent context，CDP 作为可选高级模式，cookie import 作为兜底能力。

### 默认路径

```text
~/.mediacrawler-mcp/browser_profiles/
  xhs/default/
  dy/default/
```

后续支持多账号时扩展为：

```text
~/.mediacrawler-mcp/browser_profiles/
  xhs/<account_id>/
  dy/<account_id>/
```

### CDP 定位

CDP 不是免登录方案。它用于连接或启动真实浏览器，并复用该浏览器 profile、cookie、localStorage 等登录状态。

CDP 不作为第一版强依赖，但保留配置入口：

```yaml
browser:
  mode: persistent_context
  cdp_endpoint: null
```

### cookie import 定位

cookie import 用于服务器兜底：

- 无法扫码。
- 需要从本地浏览器导出 cookie。
- 登录验证复杂。
- 需要快速恢复登录态。

小红书后续应尽量保留完整 cookie string，不要只保存 `web_session`。

## 9. 二维码与飞书边界

### 决策

二维码主通道使用本地图片路径。

```json
{
  "qr_image_path": "/tmp/mediacrawler-login/xhs-login-20260627.png",
  "qr_image_base64": null,
  "expires_in_seconds": 120
}
```

### 理由

- Hermes 在飞书场景下更适合发送本地媒体文件。
- base64 会放大 MCP 返回体，也不适合进入 LLM 上下文。
- 文件路径便于调试、复用和过期清理。

### 边界

MediaCrawler MCP 负责：

- 生成二维码文件。
- 返回二维码路径。
- 维护登录会话状态。
- 返回登录成功、过期或失败状态。

Hermes 负责：

- 上传飞书图片。
- 发送飞书消息或交互卡片。
- 保存用户原始请求。
- 登录成功后恢复采集任务。

MediaCrawler MCP 第一版不引入飞书 SDK。

## 10. 报告与分析栈

### 决策

第一版使用：

- pandas
- jieba
- wordcloud
- DuckDB
- Markdown
- HTML

### 报告内容

主题调研报告至少包含：

- 数据集信息。
- 平台范围。
- 关键词范围。
- 采集时间。
- 内容数量。
- 评论数量。
- 高互动内容 Top N。
- 高频评论词。
- 用户主要关切。
- 典型正面反馈。
- 典型负面反馈。
- 疑似广告或引流内容。
- 值得人工复看的链接。

### 智能分析边界

MCP 负责结构化统计、规则识别和候选样本输出。

Hermes 负责自然语言归纳总结。

第一版不把复杂 LLM 总结写死在 MCP 内部。

## 12. 第一版开发顺序

### Phase 1：MCP 壳与数据集元数据

- 初始化 stdio MCP server。
- 初始化 SQLite。
- 实现 `create_dataset`、`list_datasets`、`get_dataset`。
- 创建标准数据集目录。

### Phase 2：小红书单平台最小闭环

- 实现 `get_login_status`。
- 实现 `start_login`，输出二维码图片路径。
- 实现 `wait_login`。
- 实现 `start_collection` 和 `get_task_status`。
- subprocess 调用 MediaCrawler。
- 输出 raw JSONL。

### Phase 3：DuckDB normalize 与查询

- raw JSONL 导入 DuckDB。
- 标准化 `contents` 和 `comments` 表。
- 实现 `query_dataset`。
- 支持按平台、关键词、互动数、评论数过滤和排序。

### Phase 4：报告生成

- 实现 `generate_report`。
- 输出 Markdown、HTML、summary JSON。
- 复用并扩展当前 `analysis` 包。
- 增加广告/引流规则识别。

### Phase 5：多平台与多关键词

- 接入抖音。
- 支持多关键词串行或受控并行。
- 报告支持 `source_keyword` 对比。
- 支持历史数据集复用。

## 13. 已采纳与暂缓清单

### 已采纳

- stdio MCP。
- SQLite 管任务和元数据。
- subprocess 执行采集。
- JSONL 原始归档。
- DuckDB 分析查询。
- Dataset first 的 MCP 接口。
- `source_keyword` 进入所有核心记录。
- Playwright persistent context 默认登录态。
- CDP 可选。

### 暂缓

- HTTP MCP。
- Celery、Redis Queue、RQ。

- MCP 内置飞书 SDK。

- 大规模并发采集。

## 14. 开放问题

- Hermes 的 stdio MCP 配置格式需要以实际服务器配置为准。
- 小红书二维码生成需要验证当前 MediaCrawler 登录流程是否能稳定输出 PNG。
- 抖音登录态是否需要额外保存 localStorage，需要单独验证。
- subprocess 采集产物如何直接写入 dataset raw 目录，需要在实现阶段确认最小改造点。
- DuckDB 是否每个 dataset 一个库，还是全局一个库，需要根据查询复用方式最终确定。第一版倾向每个 dataset 一个 `analysis.duckdb`。
